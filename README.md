# Minecraft Canvases

Turn a Minecraft painting into a paint-by-numbers chart, so you can paint it in real life.

Pick one of the 50 Java Edition paintings and the app shows every pixel as a numbered square, plus a palette with the hex and RGB code of each paint and how many squares need it.

## Features

- **Painting picker** with all Java Edition 1.21 paintings, grouped by size in blocks like the [Minecraft Wiki's Painting page](https://minecraft.wiki/w/Painting), with search.
- **Numbered chart** at full width, with spreadsheet-style coordinates (A, B, C… across, 1, 2, 3… down) and a heavier line every 16 pixels (one block). Cell size starts at whatever fills the screen and can be adjusted.
- **Color simplification:** reduce a painting to 2–64 paints (or keep every exact color) with a deterministic weighted k-means. Paints are numbered dark → light, which is handy for layering.
- **Highlight a paint:** click a palette row to dim everything else and see only the squares that need it.
- **Copy the color list** as tab-separated text for a spreadsheet or notes app.
- **Print:** prints the chart with your color and display settings, scaled to fit the page. Choose the paper (A4, Letter, A3), orientation (auto picks landscape for wide paintings), and whether to include the title and a color list on a second page. Ctrl/Cmd+P works too.
- Light and dark themes; remembers the last painting you picked.

## Getting started

Requires Node.js 20.19+ (see `.nvmrc`).

```sh
npm install
npm run dev        # start the dev server at http://localhost:5173
```

| Script                | What it does                                              |
| --------------------- | --------------------------------------------------------- |
| `npm run dev`         | Dev server with hot reload                                |
| `npm run build`       | Type-check and build the static site to `dist/`           |
| `npm run preview`     | Serve the built `dist/` locally                           |
| `npm test`            | Unit tests (Vitest)                                       |
| `npm run test:e2e`    | End-to-end tests (Playwright) against the production build |
| `npm run test:e2e:ui` | Playwright's interactive UI mode                          |
| `npm run typecheck`   | Type-check the app, unit tests and e2e tests              |
| `npm run check`       | Type-check and unit test                                  |

The first time you run the e2e tests, install a browser with `npx playwright install chromium`.

## Deployment

Every push to `main` builds the app and publishes `dist/` to GitHub Pages (`.github/workflows/deploy.yml`). In the repository's **Settings → Pages**, the source must be set to **GitHub Actions**. Asset paths are relative (`base: './'` in `vite.config.ts`), so the build works under `/minecraft-canvases/` or any other path.

CI (`.github/workflows/ci.yml`) runs the type-check, unit tests, build and the Playwright suite on every pull request.

## Project structure

```
index.html                  Empty shell with #app (Vite entry)
public/paintings/           One PNG per painting, named by its Minecraft texture id
public/favicon.svg, icons   Logo and app icons, generated by scripts/generate-logo.py
src/
  main.ts                   Mounts the page
  styles/                   Design tokens (colors, fonts, dark mode) and base element styles
  components/               UI, organized with atomic design (each component has its own .css)
    atoms/                  Smallest pieces: Button, Switch, Slider, Heading, Logo, Text, Swatch, Panel…
    molecules/              Small groups of atoms: Field, RangeField, SegmentedControl, SettingsGroup, PaintingCard, PaletteRow…
    organisms/              Page sections: PaintingPicker, ChartSettings, ChartCanvas, PalettePanel, PrintSheet…
    templates/              Layout only: WorkbenchTemplate places the sections, no behavior
    pages/                  ChartPage owns the app state and wires the organisms together
  data/
    paintings.json          Painting manifest: id, wiki name, size in pixels
    paintings.ts            Typed access, image URLs, grouping and search
  lib/                      Framework-free logic, unit tested
    quantize.ts             Pixels → chart: unique colors, k-means reduction, numbering
    render.ts               Draws a chart onto a <canvas>
    crop.ts, color.ts, export.ts, image.ts
tests/                      Vitest unit tests, including a manifest/PNG consistency check
e2e/                        Playwright tests, run on desktop and mobile Chrome
```

The stack is deliberately small: **Vite + TypeScript**, no UI framework. Components are plain functions that return DOM elements; components with state return a small handle (for example `{ root, update() }`). Data flows down through props and back up through callbacks, so only the page knows about more than one organism. The chart logic in `src/lib/` has no DOM dependencies beyond the canvas renderer, so it is tested in Node.

### Writing components

- **Atom**: one element, no knowledge of paintings or charts beyond simple props.
- **Molecule**: a few atoms with one job (a labelled field, a palette row).
- **Organism**: a self-contained section that may hold its own UI state (search query, settings) and reports changes through callbacks.
- **Template**: arranges slots, no state.
- **Page**: the only place app state and data loading live.

Give interactive elements accessible names (labels, `aria-label`, `aria-pressed`): the e2e tests find elements by role and name, not by CSS classes.

## Adding or updating a painting

1. Put the texture PNG in `public/paintings/`, named after its Minecraft id (for example `public/paintings/wanderer.png`). Java textures live in the game jar under `assets/minecraft/textures/painting/`.
2. Add an entry to `src/data/paintings.json`:
   ```json
   { "id": "wanderer", "name": "Wanderer", "width": 16, "height": 32 }
   ```
   `width` and `height` are in texture pixels (16 per block).
3. Run `npm test`. It fails if a PNG is missing, unlisted, or a different size than the manifest says.
